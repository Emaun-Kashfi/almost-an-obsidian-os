# Three changes — CONTRACT (today = 2026-09-13)

Vault: the Storm Dashboard, built from `dev/` (one variant per `dev/<name>/variant.json`).
Field names, panel code and CSS are shared by every variant; a change lands in all of them.

────────────────────────────────────────────────────────────────────────────
## A. `dv.view()` refactor — stop embedding the panel in every note

**Problem.** `_scripts/task-gantt.txt` (25 KB) and `_scripts/goal-panel.txt` (22 KB) are pasted
verbatim into every task and goal note. Eleven live notes have now been rewritten three times in one
day to ship panel changes, and every rewrite is a full-file write to a note the user also edits.

**Target.** The panel lives in ONE file per vault; a note carries a one-line block:

```dataviewjs
await dv.view("_scripts/task-gantt")
```

- Dataview resolves `dv.view("p")` to the vault file `p.js` (or `p/view.js`) and runs it with `dv`,
  `input` and `this` in scope. Ship `_scripts/task-gantt.js` and `_scripts/goal-panel.js`.
- Inside a view, `this.container` is NOT the render container — the panels currently open with
  `const root = this.container;`. Change to `const root = dv.container;`, which is correct in both a
  view and an inline block, and verify it renders in a real Obsidian-shaped DOM, not only the harness.
- Keep the `try { … } catch` wrapper and the error div: a missing or broken view file must degrade to
  a visible message in the note, never a silent blank.
- The `.txt` panel sources are replaced by the `.js` files. Anything that embedded them
  (`integrate.py` panel markers, `assemble_dashboard.py`'s `GOAL_PANEL`, the Goal and Task
  templates, and the Dashboard's `task:` quick-add route)
  now emits the one-line block instead. The Dashboard's own copy of the goal panel disappears —
  expect `Dashboard.md` to shrink by ~22 KB.
- **Migration tool**: extend `dev/tools/refresh_blocks.py` (or replace it) with a mode that
  rewrites an existing note's embedded panel block down to the one-liner, changing nothing else.
  It must refuse any note that does not contain exactly one fenced `dataviewjs` block.
- **Harness**: `dev/tests/harness.js` currently
  stub `dv.view` as `async () => {}` — a no-op. Every test would then pass while rendering nothing.
  Implement it for real: resolve the path against the store (`p.js`, then `p/view.js`), run the
  source with the same `dv`/`app`/container contract as `runBlock`, and propagate errors. Add a test
  that a missing view file produces the error div, so the stub can never silently return.

## B. The theme must apply to the whole vault, not just the Dashboard

**Problem.** `helpers.js` `_themeRule(t)` scopes every declaration to
`body:not(.theme-light) .storm-hub` (plus a `.storm-home` page-background rule), and emits it as a
`<style class="storm-theme-css">` INSIDE the Dashboard note's own output. So the palette derived
from the banner image ("Match image" mode) dies at the edge of the Dashboard: goal notes, task
notes, 🎯 Goals, 📋 Tasks, 🧹 Triage and daily notes all keep the hardcoded blue.

**Target.** The chosen theme paints every Storm surface in the vault, and survives a restart.

1. **Indirection.** Every palette declaration block — `base/.obsidian/snippets/storm.css` ≈950
   (`.dashboard, .goalpanel, .dt-wrap, .triage, .goalsidx, .tasksboard`) and each local palette in
   `storm-additions.css` (`.tgantt`) — changes
   from a literal to `var(--storm-<name>, <the current literal>)`. The literal stays as the
   fallback, so a vault with no theme file looks exactly as it does today.
2. **A real snippet file.** When the theme changes, the Dashboard writes
   `.obsidian/snippets/storm-theme.css` via `app.vault.adapter.write`, containing the palette as
   `--storm-*` custom properties on `body` (plus a `body.theme-light` block where the palette is
   light). Obsidian reloads snippets on file change, so it applies immediately and persists.
   Add `"storm-theme"` to `enabledCssSnippets` in `appearance.json` in both vault builds, and create
   the file at build time with the default palette so a fresh vault has it.
3. **Community mode** maps `--storm-*` to the installed theme's own variables
   (`--background-primary`, `--interactive-accent`, …) — the same mapping `_themeRule` already uses.
4. Keep the in-Dashboard `<style>` as well so the Dashboard repaints instantly on preview, but it
   must no longer be the only carrier.
5. Verify by rendering a goal note, a task note and 📋 Tasks with a match-mode theme file present
   and confirming the accent actually changes — not just that the file was written.

## C. Accessibility: colour contrast must not regress

`helpers.js` already WCAG-corrects the image-derived palette (`_fixText` / `_fixAcc`, target 4.5).
That covers `--dim`, `--faint`, `--accent`, `--accent2`, `--warm`, `--good` against `--bg`,
`--surface`, `--surface2` — but nothing checks the STATIC palettes, the health badges, the paused
badge, the Gantt bar labels, or the light/e-ink theme.

**Target.** An automated audit, then fixes, then the audit runs in CI as a suite.

- Build `dev/a11y/audit.js`: render each surface (Dashboard, goal panel, task Timeline,
  🎯 Goals, 📋 Tasks, 🧹 Triage, daily tables) in a real browser with the vault's REAL shipped
  `storm.css`, walk every element with text, read the COMPUTED colour and the effective background
  (walking ancestors through transparent backgrounds; treat an SVG `fill` as the colour and the
  nearest painted ancestor as the background), and compute the WCAG 2.1 contrast ratio.
- Fail anything below **4.5:1** for normal text and **3:1** for large text (≥24px, or ≥18.66px at
  weight ≥700) and for the non-text boundaries that carry meaning (chart bars against the chart
  ground, the today line, focus rings — 3:1).
- Run the matrix: dark × light, community × match, and at least four derived palettes spanning very
  dark, very light, highly saturated and near-grey source images.
- Fix every failure by adjusting the palette or the rule, never by hiding the element. Prefer
  lifting a colour to adding a background. Where a fix would change the look materially, note it.
- Land the audit as a permanent suite in both repos, wired the way the other suites are.
