# AGENTS.md

Operating rules for any coding agent working in this repo. Read all of it before your
first edit. It is short on purpose.

This file is vendor-neutral. It assumes nothing about which tool is reading it. If your
tool only auto-loads a file named after itself, ask the human to add a one-line stub that
points here. Do not add one yourself.

The long explanation lives in `dev/ARCHITECTURE.md`. Read that before changing a rule.

---

## 1. The vault is build output

`Storm Dashboard Vault/` is generated. Every file in it comes from `dev/`.

**Never hand-edit anything under `Storm Dashboard Vault/`.** The next build overwrites it,
your change disappears, and nothing warns you. This is the most likely way to waste a
session in this repo.

Generated, do not touch:

- `Storm Dashboard Vault/Dashboard.md` comes from `dev/dashboard/{helpers,buildHub,initHub,livedata}.js`.
- `Storm Dashboard Vault/_scripts/*`, `Goals/🎯 Goals.md`, `Tasks/📋 Tasks.md`,
  `🧹 Triage.md`, `_templates/*` come from `dev/common/`.
- `Storm Dashboard Vault/.obsidian/snippets/storm.css` is the vendored base stylesheet plus
  `dev/common/storm-additions.css`, concatenated by the build.
- `Storm Dashboard Vault/.obsidian/snippets/storm-theme.css` is generated by the build and
  rewritten by the dashboard at runtime.

Edit the source, run the build, commit both. The build is idempotent, so a rebuild with no
source change produces a byte-identical tree. If `git status` shows vault files you did not
expect, you changed more than you meant to.

## 2. Four rules, duplicated byte-for-byte

A `dataviewjs` block in a note cannot import anything, so every block carries its own copy
of the shared rules. These four are duplicated **byte-for-byte** on purpose:

| Rule | Does |
|---|---|
| `subMarks` / `subsOf` | decides which checkboxes count as sub-tasks |
| `healthOf` + `HL` + `HORDER` | the health label and its sort order |
| `clean` | strips Tasks-plugin emoji, dates, tags and block ids |
| `linkNames` / `linkKeys` | resolves a `goal:` value to a name |

They live in `dev/dashboard/livedata.js`, `dev/common/_scripts/goal-panel.js`,
`dev/common/_scripts/task-gantt.js`, `dev/common/Goals/🎯 Goals.md`,
`dev/common/Tasks/📋 Tasks.md` and `dev/common/_scripts/daily-tables.txt` (two blocks, so
two copies). `dev/common/🧹 Triage.md` carries the `#habit` regex only.

**Change every copy identically, or change none.** Count `subsOf` in a clean checkout and
you find sixteen copies: seven in `dev/` that you edit, and nine inside
`Storm Dashboard Vault/` that the build writes.

`dev/tests/V/shared_rules.py` extracts each one from the built vault and fails if they are
not character-identical. `tests/H` and `tests/P` pin specific lines of `healthOf`. When
those fail, they are telling you that you edited one copy.

Every previous fork of these rules produced a real bug where two screens showed different
numbers for the same note. `dev/ARCHITECTURE.md` section 10 lists them.

## 3. Goal and task notes carry a three-line loader

A goal or task note holds one `dataviewjs` block of three lines. It resolves
`_scripts/<panel>.js`, calls `dv.view` on it, and renders a message when the file is not on
this device. The panel code lives in exactly one file and is **never** pasted into a note.

Five places emit that block and all five must stay byte-identical: `view_block()` in
`dev/integrate.py`, `viewBlock()` in `dev/dashboard/initHub.js`, and the same helper in
`dev/common/_scripts/goal-panel.js`, `dev/common/Goals/🎯 Goals.md` and
`dev/tools/refresh_blocks.py`.

If you need to rewrite that block in notes that already exist, use
`dev/tools/refresh_blocks.py --view _scripts/<panel> --dry-run` first. It refuses any note
that does not hold exactly one fenced block, and it preserves every other byte.

## 4. Build and test

```sh
cd dev
npm install          # Playwright downloads a browser here
npm run build        # assemble_dashboard.py + integrate.py
npm test             # suites A B1 B2 E G2 H P T V W
npm run test:a11y    # colour-contrast audit
```

**A change is not done until `npm test` and `npm run test:a11y` both pass.** Suites re-run
the build and assert against the built vault, not the sources, so a green run proves the
shipped file works.

Several suites write PNG screenshots. Those are evidence for a human, not assertions. If
you changed anything visual, look at them.

## 5. Log what you changed

Every change set adds one entry to the top of `dev/DEVLOG.md`, newest first:

```markdown
## 2026-09-14 · short title
**Agent:** <your tool and model> · **Human:** <who asked>
**Why:** one or two sentences on the problem, not the diff
**Changed:** the files, grouped
**Verified:** which suites ran and their result
**Risks / follow-ups:** anything left
```

Name yourself and your model honestly in the `Agent:` line.

A pre-commit hook enforces this. A commit that touches `dev/` or `Storm Dashboard Vault/`
must also stage `dev/DEVLOG.md` with a new top entry. **The hook is not active until a
human runs `sh dev/hooks/install.sh` in their clone.** If it is not installed, write the
entry anyway.

Two escape hatches exist: `git commit --no-verify`, or `[skip devlog]` in the commit
message. Use them for a genuinely unrelated commit, not to skip the log.

## 6. This repo is public

Nothing personal or work-related goes in, in any file including tests and fixtures. No real
names, no private vault content, no email addresses. No absolute paths such as
`/home/...` or `/Users/...`. Every path in a shipped file resolves from the repo root, so a
clone works anywhere.

## 7. Traps worth knowing before you start

The build or a test enforces every one of these. `dev/ARCHITECTURE.md` explains why each
exists, which is what stops you from removing it.

- **Inside a `dv.view` file, `this` is the global object.** Render into `dv.container`. A
  view file is bare JavaScript with no code fence. The build rejects both mistakes.
- **Do not use `processFrontMatter` in a panel.** It reorders and reformats a user's
  properties block. Panels use their own line-based `setFm` / `delFm`, which patch in place
  and preserve CRLF.
- **The pause cascade is computed, never written.** Pausing a goal must not rewrite its task
  notes. A task's effective paused state is its own status or its goal's, resolved at read
  time.
- **Health forks on whether any sub-task has a date**, not on whether any is overdue. Dates
  present means count overdue items. No dates anywhere means fall back to pacing.
- **Line writes never use a substring match.** Find the exact checkbox by normalised text,
  refuse on zero or multiple matches, and keep a trailing `^block-id` last on the line.
- **Keep `dev/dashboard/buildHub.js` pure.** No `dv`, no `app`, no file reads. The render
  tests depend on it.

## 8. Before you finish

1. `npm run build` and confirm the vault diff is only what you intended.
2. `npm test` and `npm run test:a11y`, both green.
3. If you touched a shared rule, confirm every copy changed.
4. Add the `dev/DEVLOG.md` entry.
5. Re-read any assertion you changed and say in the log why the new value is right.
